# Bugs & Fixes Log

Every bug hit during implementation, with root cause and fix, so a future session never re-debugs the same
thing. Log a bug here **before** reporting back to the user for the part it occurred in.

| Date | Symptom | Root cause | Fix | Files affected | Phase/Part |
|---|---|---|---|---|---|
| 2026-09-29 | `boto3` S3 calls to B2 (`head_bucket`/`list_objects_v2`) failed with `InvalidAccessKeyId: Malformed Access Key Id` (403), repeatedly, across multiple regenerated secrets | The credential in use was the **Master Application Key**, whose `keyID` always equals the 12-char Account ID. This is valid for B2's native API (confirmed via direct `b2_authorize_account` call — succeeded every time) but is rejected by B2's S3-compatible gateway, which requires a real non-master Application Key's longer (~25-char) `keyID`. Compounded by an earlier, separate mistake: the `BUCKET-ID` env var holds B2's internal bucket ID (hex), not the bucket *name* the S3 API's `Bucket=` parameter needs. | Created a genuine non-master Application Key scoped to the bucket (25-char keyID, 31-char secret) via B2 console → App Keys → "Add a New Application Key" (not "reset master key"); used the real bucket name (`satilliate-images`, from the console) instead of `BUCKET-ID`'s value. | `.env` (user-side), no repo code | Phase 0, Part 0.4 |
| 2026-10-10 | `pip install rasterio rioxarray geopandas ...` produced a dependency-resolver conflict: `scikit-learn`/`matplotlib`/`scipy` require `numpy<2.0`, but the current `rasterio`/`geopandas`/`rioxarray` require `numpy>=2.0` | The Studio's pre-installed ML packages (`scikit-learn 1.3.2` etc.) predated numpy 2.0 and were older than this project's own `pyproject.toml` pins; installing the geospatial stack piecemeal upgraded numpy without upgrading its dependents | Upgraded the whole numpy-dependent set together in one `pip install` call (`numpy`, `scikit-learn`, `matplotlib`, `scipy`, `pandas`, `xgboost`, `lightgbm`, `shap`) so pip's resolver picked one mutually-compatible set; verified with `pip check` (no broken requirements) and a full cross-import smoke test. Updated `pyproject.toml` pins to match the new tested-compatible versions (numpy 2.x, scikit-learn 1.9.x, etc.) instead of the original Part 0.1 guesses. | `pyproject.toml` | Phase 0, Part 0.4 |
| 2026-10-10 | Real inventory run showed 352 objects (24%) misclassified as generic `other` instead of `sentinel2` | `product_id.py`'s regex only recognized the full per-scene product-ID naming; the bucket also has a second, shorter "mosaic" composite naming with no tile/baseline (`S2A_20180103T045201_R076_refl.tif`) | Added `_MOSAIC_RE` and a `mosaic_derivative` format branch; extended completeness grouping in `inventory.py` to cover it | `src/acquisition/product_id.py`, `src/acquisition/inventory.py` | Phase 2, Part 2.1 |
| 2026-10-10 | After the fix above, 280 objects were still `sentinel2/unrecognized` — turned out to be the entire raw archive | The raw zipped archive is named `<product_id>.SAFE.zip`, not plain `<product_id>.zip` as the parser assumed; this is also what caused the premature "A1 confirmed, no raw archive" note from Part 0.4 to be wrong (that was a 10-key sample that happened not to include any `.SAFE.zip` files) | Added `.SAFE.zip` as a second recognized zip-remainder pattern | `src/acquisition/product_id.py` | Phase 2, Part 2.1 |
| 2026-10-10 | `test_no_hardcoded_paths` false-flagged two literals in new Part 2.3 code: a dict key `"results"` in a return value, and `"/IMG_DATA/"` used as the right operand of an `in` membership test | The lint's `_looks_like_project_path_literal` heuristic matches by string VALUE only, with no awareness of syntactic context — a dict key or a substring-test operand can coincidentally match a project top-dir name or a leading `/` even though neither is ever used as a path | Added `_non_path_usage_ids()`: exempts `ast.Constant` nodes that are dict keys or operands of an `In`/`NotIn` comparison, with 3 regression tests (including one proving the exemption isn't a loophole for a real hardcoded path used as a dict *value*) | `tests/unit/test_no_hardcoded_paths.py` | Phase 2, Part 2.3 |
